# 本地 embedding 方案（2.0.0-alpha.8 起，已实现并随 2.0.0 发布）

> 状态：已实现。契约自 `2.0.0-beta.1` 冻结、随 `2.0.0` 生效（工具参数 / 宿主 op / 设置键 / `index/vectors.json` v2 格式），默认值仍按评测证据调整。
> 前置：`docs/memory-recall-v2.md`（词法 + 图召回的整体设计）。本文件只讲「把语义向量加进日志层」这一段。

## 1. 结论

- **只在日志层做语义**：`journal` 笔记 + `memory` 记忆日志，共 150 条、12.4 万字（≈8.3 万 token）。知识库和会话原文继续纯词法。
- **模型本地跑**：BAAI `bge-small-zh-v1.5`（int8 量化，24 MB，512 维），不依赖网络、不上传任何记忆内容。
- **混合打分**：两路**按名次**用 RRF 融合（`0.6/(k+词法名次) + 0.4/(k+语义名次)`，`k=20`）——余弦与词法分不同量纲，先归一化再加权会被单边压死；余弦低于 **0.45** 的命中丢弃（噪声探针峰值 0.424），语义行不作为图扩展种子。
- **失败即降级**：模型缺失 / 加载失败 / 超时 → 本次查询退回纯词法，原因写进 `index/state.json`，面板可见，`agent_recall` 调用方不感知报错。
- **红线不变**：向量与检索结果只走工具返回值，绝不进 system prompt / 动态 context（否则缓存前缀整段重付）。

## 2. 为什么是「日志层」而不是全量

| 层 | 规模 | 嵌不嵌 | 理由 |
|---|---|---|---|
| 检查点 L0 | 5 条 | 否 | 权威状态，永远整段注入，进索引没有意义 |
| 4K 记忆 L1 | 1 段 | 否 | 同上，恒注入 |
| journal 笔记 | 32 条 / 4.1 万字 | **是** | 自然语言、中文同义改写多，词法错配最严重 |
| 记忆日志 log | 118 条 / 8.3 万字 | **是** | 同上，且追加写、失效成本低 |
| 知识库 | 21 条 | 暂否 | 专有名词密集，词法本来不差；先拿日志层验证收益 |
| 会话原文 | 110 个会话 / 52 MB | 否 | 分块、脱敏、失效三件事都没解，代价远超收益 |

### 3.2 为什么选它

| 候选 | 维度 | int8 体积 | 中文效果 | 取舍 |
|---|---|---|---|---|
| **bge-small-zh-v1.5** | 512 | 24 MB | 强（中文检索榜前列） | 选定：体积/效果最平衡 |
| bge-base-zh-v1.5 | 768 | ~100 MB | 更强 | 内存与首次加载翻倍，日志层这点语料用不上 |
| bge-m3 | 1024 | ~560 MB | 最强、多语 | 太重，108 MB → 不适配「随插件跑」 |
| multilingual-e5-small | 384 | ~120 MB | 中 | 多语均衡，中文不如 bge 小模型 |
| text2vec-base-chinese | 768 | ~400 MB | 中上 | 老一代，句子级效果弱于 bge |

int8 量化对短文本检索的损失通常在 1–2 个点 top-1 以内；如果实测掉得明显，同一仓库有 `model_fp16.onnx`（47 MB）可直接替换，配置里改文件名即可。

### 3.3 何时切换 fp16

- 评测里 int8 的 top-1 比 fp32 低 > 3 个点；
- 或者出现「同一句话两次嵌入余弦 < 0.98」这种量化伪影。

## 4. 运行时

宿主插件跑在 Electron 主进程里，选型按「先短路径、可回退」排：

1. **`onnxruntime-node`**（N-API，跨 Electron ABI 稳定）+ 自写 WordPiece 分词（`vocab.txt` 驱动，BGE 用 BERT 分词，含中文单字切分）。
2. 若 Electron 里加载 native 失败 → **`onnxruntime-web`（wasm）**，同一份 `model_quantized.onnx`，纯 JS 加载，慢 2–4 倍但语料小、可接受。
3. 若 wasm 也不稳 → **子进程**：`node scripts/embed-server.mjs` 用系统 Node 跑，插件通过 stdin/stdout 通信；最后手段，因为多一个进程要管。

不选 `@huggingface/transformers` 全家桶：它会隐式联网下载模型、依赖面大、Electron 兼容性不确定；我们只需要「一个 tokenizer + 一次 session.run」，自己写约 150 行，可控且可测。

**实测**（本机 Ryzen + Node 24 / Electron 44）：session 创建 150 ms（一次性，启动时 `setTimeout` 预热）；3 条文档嵌入 8 ms；单查询 20 ms（12 条改写查询均值，含分词 + 嵌入 + 全量点积；模型加载另计 150 ms，启动时预热）；常驻内存未单独测，24 MB 权重 + ORT arena，估 50–80 MB RSS。

`embed.js` 用 `createRequire` 惰性 `require('onnxruntime-node')`：依赖缺失只让 `embedder` 变 `null`（检索退回词法），不会让插件加载失败。

## 5. 目录与文件格式

```
<root>/
  models/bge-small-zh-v1.5/…        模型（不入 git、不打进 npm 包）
  index/vectors.bin                 float32 小端，一行一个分块（chunk），按 entries 顺序紧密排列
  index/vectors.json                {version:2, model, dim:512, builtAt, entries:[
                                      {key:"journal:<id>", row:"journal:<id>#0",
                                       src, at, hash, chunk:0, chunks:3} ]}
  index/state.json                  增加 semantic:{model, count, builtAt, lastError}
```

- `hash = sha256(title + "\n" + text).slice(0, 16)`：**按条目内容判脏**。日志文件追加写会让 mtime 整文件变，用 mtime 会每次保存都全量重嵌。

向量库是**全库一份**（所有智能体的日志层一起嵌，key 形如 `journal:j-xxxx` / `log:<agentId>:m-3`）：只嵌调用方的智能体会让两个智能体互相把对方的行挤掉，交替查询时每次都要重嵌上百条。日志条目的 id 在一个文件内是位置序号（`m-3`），所以 key 必须带智能体前缀，否则跨智能体撞键。
- **一条笔记可以有多行**（分块，见 §7.2）：`row` 是行 id（`key#chunk`），`chunks` 是该笔记的分块数；v1 的「一行一条」布局在读到时直接作废重建，不做迁移。
- 向量归一化后存（L2=1），检索时只需点积。
- 删除条目：`bin` 整文件重写并收缩（`sync()` 里做），不保留空槽——150 条的量级重写只要几毫秒，空洞+定期压缩不值得。

## 6. 流程

### 6.1 下载模型（首次）

```
node scripts/fetch-model.mjs [--dir <modelsDir>] [--force]
memory.model {action:"status"}    → state().semantic（模型名 / 维度 / 已嵌条数 / 降级原因）
memory.model {action:"prepare"}   → 预加载模型 + 增量建库
```

- CLI 逐文件下载，镜像 hf-mirror.com → huggingface.co；**逐文件校验 size，全部文件校验 sha256**（6 个文件的 size/sha256 写死在脚本里，本次下载即按此校验）。
- 续传：文件已存在且 size+sha256 正确就跳过，所以中断后重跑即可；`--force` 覆盖。
- 模型不打进 npm 包（`files` 白名单不含 `models/`）。
- 面板的「准备 / 同步向量」按钮复用同一份文件清单与同一个 `memory.model` op（`2.0.0-alpha.10` 落地；模型不存在时按钮直接给出下载命令，不在界面里下载）。

### 6.2 建库 / 增量

```
memory.reindex  → 全量：清 vectors，逐条嵌入，写 vectors.bin + vectors.json + state.json
首次查询        → 若 vectors.json 不存在或 model 变了：后台建库（查询本身走词法先返回）
日志写入后      → 不主动嵌；下次查询时对 hash 变化的条目补嵌
```

**分块而不是截断**（alpha.13 起）：编码器只读 512 token，而本库笔记的中位数是 654 token、28 条里 22 条超限（`eval/token-check.mjs`），整条嵌入等于把尾部细节丢掉。做法是按约 420 字切窗口（重叠 60 字、尽量落在句末），每个窗口前面重复标题，一条笔记因此对应多行向量；相似度取**各窗口的最大值**——平均值会让别的段落冲淡真正对上的那一段。`chunkChars: 0` 回到整条嵌入。

### 6.3 检索（hybrid）

1. 词法：现有 `rank.js`，得带分排序（别名命中已并入这一步）。
2. 语义：查询嵌入一次（**加 BGE 查询指令前缀**，文档不加），对全部条目点积得 `cos`。
3. 过滤：`cos < minCosine` 的条目没有语义名次（默认 0.45，见 §7.1）。
4. 融合：**倒数排名融合（RRF）**，`score = 0.6/(20+lexRank) + 0.4/(20+semRank)`，缺哪一路就少加哪一项。
5. `via` 扩展为 `lexical | alias | ref | entity | session | semantic`，面板按值出徽标；语义独有命中显示「语义」而不是「关联」。
6. 图扩展（`expand`）只作用于词法/别名种子，不拿语义命中当种子——共现边与语义空间是两套结构，混用会把两者的噪声相乘。

**为什么不是加权和**：先按 `0.6*norm(lex) + 0.4*cos` 实现过，实测 top-1 只有 33.3%（vs 纯词法 25%）。原因是量纲：词法最大项恒被归一化成 1.0→占 0.6，而余弦常在 0.5–0.65→只占 0.2–0.26，只要某条有词法命中，正确但只靠语义的条目永远翻不上来。改成 RRF 后同一评测集 top-1 41.7%、MRR 0.528。RRF 只比名次，不存在这个量纲陷阱，且对分数的绝对值不敏感（词法分数是 `rank.js` 的经验加权，本来就不该被当成概率）。

参数进 `settings.json`：`recall: {mode:"hybrid"|"lexical", lexicalWeight:0.6, semanticWeight:0.4, minCosine:0.45, rrfK:20}`。默认 `hybrid`；`mode:"lexical"` 保留为回归开关。`weights`、`minCosine`、`rrfK` 均可按次覆盖（评测脚本用，见 `recall.search` 的 `input.weights` / `input.minCosine` / `input.rrfK`）。这些默认值不是手定的，来源见 §7.1。

### 6.4 失败与降级

| 情况 | 行为 |
|---|---|
| 模型文件缺失 | 本次查询词法；`state.semantic.lastError = "model-missing"` |
| 加载失败（ABI/内存） | 同上 + 面板提示「语义不可用：<原因>」 |
| 单次嵌入 > 1.5 s | 放弃语义，走词法；不重试 |
| 条目文本为空 | 跳过，不占向量槽 |

任何情况下 `agent_recall` 都能正常返回——语义层是增强，不是依赖。

### 6.5 面板

「回忆」页签新增「语义索引」卡片（`2.0.0-alpha.10` 落地）：

- 模型名 / 维度 / 已嵌条数 / 最近建库时间 / 是否降级及原因（数据由 `memory.model {action:"status"}` 提供）；
- 「准备向量」/「同步向量」按钮走同一个 `memory.model {action:"prepare"}`；模型缺失时按钮禁用并显示 `node scripts/fetch-model.mjs`（下载放在 CLI，不在界面里做进度条——24 MB 的下载中断与校验逻辑已经写在脚本里，重造一遍没有收益）。

搜索框旁出现 `mode` 切换（hybrid / lexical），用来看「这句话语义找到了什么」，也方便把一次可疑的召回退回纯词法复现。

## 7. 评测（先于实现）

`eval/recall-paraphrase.mjs`：12 条**改写查询**（答案不变、说法变，且与目标笔记没有字面重叠），跑 `mode:"lexical"` 与 `mode:"hybrid"` 各一遍，报 top-1 / top-3 / MRR / 平均延迟 / 排名变化 / 语义独有命中。

| 查询 | 期望命中（作者自己的 journal） | 纯词法排名 | hybrid 排名 |
|---|---|---|---|
| 会话怎么被收起来 | 1.2.0-beta.3 自动弱归档 | 10 | 15 |
| 两个会话之间怎么接上 | 接力 v1 落地 | 19 | 6 |
| 装大模型踩了什么坑 | 9B 下载 + Ollama 接入 | 6 | 5 |
| 改完名字就打不开 | 改名导致启动崩溃 | 8 | **2** |
| 上下文怎么这么短 | bili 报 6144 窗口 | miss | 6 |
| 这个对话算谁的 | 1.2.0-beta.1 对话归到智能体 | 3 | 20 |

2026-10-29 实测（真库 `demo-agent`，28 条 journal，**全库 150 条向量**；测量前已预热，含模型加载的冷启动约 200 ms）：

| 模式 | top-1 | top-3 | MRR | 延迟 |
|---|---|---|---|---|
| lexical | 25.0% | 58.3% | 0.403 | 1 ms |
| hybrid (RRF) | **41.7%** | **66.7%** | **0.528** | 20 ms |

通过线（不达标就不合入）：**top-1 至少 +10 个点，或 MRR +0.08，且单查询延迟 < 300 ms**。RRF 版两项都过（+16.7 pt / +0.125）；加权和版只有 +8.3 pt / +0.062，当时正是靠这条线判定「不能合入」才去查融合方式。

同时 `eval/recall-baseline.mjs`（14 条词面可对的查询，强制 `mode:"lexical"`）保持 top-1 92.9% / top-3 100% / MRR 0.952——语义层不许动词法基线。

> **注意：上表是 alpha.8 当时的 12 条用例。** alpha.11 做参数化时给每条改写查询查了「纯词法下的真实名次」，其中 6 条其实词法已经排第一——它们量不出语义收益，只会把平均值往上抬。这 6 条移入 `eval/cases.mjs` 的 `DROPPED_CASES` 留档，另补 9 条词法完全够不着的。所以下面的 15 条版本数字更低，但那是更诚实的数字，两版不可直接比较。

### 7.1 参数是怎么定的（2.0.0-alpha.12）

alpha.8 的 0.6/0.4、`k=20`、下限 0.45 是手定的：只有一份查询集，也没有能扫参数的工具。alpha.11 做了第一版参数化，但方法是「点估计比大小」——45 条查询上 MRR 的 95% 区间宽约 ±0.13，那个方法本来就分不出参数好坏。alpha.12 重做，有三个改变：

- **用例扩到 45 条改写、覆盖 24 条笔记**（仍是 `eval/cases.mjs` 单一来源，三个评测脚本共用）；词法已经排第一的送分题继续由 `eval/check-cases.mjs` 自动移入 `DROPPED_CASES`（累计 18 条）。
- **顺序轴代替叉积**：`eval/recall-grid.mjs` 一次只动一个轴（权重 → `k` → 下限），每个候选都在当前选择上测。16 组配置代替 150 组，全跑约 10 秒。
- **配对 + 按笔记聚类的自助法**：候选与默认值的逐查询差值重采样 4000 次（种子固定）给出 95% 区间，**含 0 就不动默认值**。重采样单位是**笔记**而不是查询——45 条查询只是 24 条笔记的 1–3 种说法，当独立样本会把区间算窄。

选择策略：

1. **权重**：各候选与默认值的配对区间全部含 0，保留 0.6/0.4。
2. **`k`**：5 / 10 / 40 / 60 的差值全部恰为 0.000，保留 20——这套打分里 `k` 几乎不起作用，不存在「衰减快慢」的取舍。
3. **余弦下限**必须在噪声探针之上：6 条无关查询把下限设为 0 时，全库最高余弦 **0.361**、中位 0.314。任何 ≤ 它的下限等于在每条无关查询上都放垃圾进来（改写集里全是有答案的问题，看不见这个代价），所以只在 0.40 以上取候选，再交给配对区间判定。

| 轴 | 与默认值的配对差值（95% 区间，按笔记聚类） | 结论 |
|---|---|---|
| 权重 0.4/0.6 | +0.007 [0.000, 0.019] | 不可区分 |
| 权重 0.5/0.5 | +0.001 [-0.010, 0.013] | 不可区分 |
| 权重 0.7/0.3 | 0.000 [0.000, 0.000] | 不可区分 |
| 权重 0.8/0.2 | -0.010 [-0.039, 0.009] | 不可区分 → **保留 0.6/0.4** |
| `k` 5 / 10 / 40 / 60 | 全部 0.000 | **保留 20** |
| 下限 0.40 | +0.006 [-0.047, 0.056] | 不可区分 |
| 下限 0.50 | -0.035 [-0.105, 0.025] | 不可区分 |
| 下限 0.60 | **-0.088 [-0.189, -0.003]** | 显著更差 → **保留 0.45** |

**这是一次自我纠正**：alpha.11 依据「0.40 的改写族 MRR 更高（+0.008）」把下限从 0.45 改到 0.40，那是一个点估计上的决定，样本量不够支撑。alpha.12 在 45 条上重测，差值是 +0.006、区间跨 0，而且 0.40 比 0.45 更靠近噪声水平 0.361——所以改回 0.45。

词法族在 hybrid 下是 100%（`mode:"lexical"` 是 92.9%）——语义把「为什么包名要改」那条唯一失手翻到了第一，跨 `k` 的每组参数都没把它弄坏（词法路径不变性检查通过）。

**这套评测的灵敏度是 ±0.128 MRR**（45 条查询 / 24 条笔记，参考配置 MRR 0.247、区间 [0.127, 0.383]；top-1 13.3%，区间 2.2%–26.8%）。比它小的差异在这里测不出来——这是判断「某次调参有没有用」的门槛，也是 alpha.11 结论站不住的根因。

**参数已经调不动了**，而且现在能说清为什么：改写族 hybrid top-1 只有 6/45、MRR 0.247，卡住它的是检索质量本身——纯语义排名下 15 条改写里目标能排第一的只有 4 条，中位名次 6/25。下一步的收益在「换更强模型 / 分块 / 标题加权」，不在参数。

**顺手否掉的一个直觉**：长笔记可能被 512 token 截断稀释，于是试了只嵌「标题 + 前 240 字」（`eval/embed-variants.mjs`）。纯语义排名确实更好（MRR 0.358 → 0.438），但无关查询的余弦也一起抬高，下限被迫升到 0.45，端到端改写 MRR 反而从 0.286 掉到 0.256。结论：整篇嵌——长笔记更具体，`vectors.js` 的 `sourceText` 上留了这段注释。

完整输出存了一份：[`eval/results/2.0.0-alpha.12.txt`](../eval/results/2.0.0-alpha.12.txt)。

### 7.2 分块嵌入（2.0.0-alpha.13）

要解决的不是 MRR，是「被截断的那部分能不能被检索到」：上限 512 token、笔记中位数 654、**22/28 条超限、合计 5,085 个 token 从未进过编码器**（`eval/token-check.mjs`）。

| 变体 | 向量行数 | 改写族 top-1 | top-3 | MRR | 与整条的配对差值 | 词法族 | 噪声峰值 |
|---|---|---|---|---|---|---|---|
| 整条（alpha.12） | 157 | 13.3% | 33.3% | 0.247 | 参考 | 100% | 0.407 |
| 420 字 | 435 | 13.3% | 33.3% | 0.253 | +0.006 [-0.066, +0.088] | 100% | 0.424 |
| 260 字 | 735 | 13.3% | 42.2% | 0.266 | +0.019 [-0.078, +0.115] | 100% | 0.430 |

（`node eval/chunk-variants.mjs`，真库 `demo-agent` 28 条笔记，45 条改写 + 14 条词法查询，每个变体在临时目录里独立建库。）

读法：**两个区间都跨 0**——「分块提升了改写族」在这套评测里不成立（灵敏度 ±0.128，差值只有 +0.006 / +0.019）。分块上线的理由是**正确性**：尾部信息不再被丢掉，而词法族不受影响、噪声峰值（0.407 → 0.424）仍在 0.45 的下限之内。260 字版本 top-3 更高，但行数多 70%、噪声更靠近下限，所以取 420 字。

`chunkChars` 通过 `createVectors` / `createRecall` 选项下传（评测脚本用它造多个独立库），默认 420，`0` 采用整条嵌入。

### 7.3 两处没接上的地方（2.0.0-beta.2）

**标题加权。** 诊断（`eval/title-vs-body.mjs`）先问「标题单独成向量值不值」：词法族 14 条上，查询与标题的余弦 0.689、与正文 0.592（差 +0.098，14/14 条更高）；改写族 45 条上反过来（-0.041，仅 10/45）。接着把它接进真实管线（标题单独一行 `chunk:-1`、`scoreMap` 按 `best = (1-w)·best + w·title` 混合、`recall.titleWeight` 夹在 0–0.5），改写族 hybrid 反而下降：

| `titleWeight` | 改写族 top-1 | top-3 | MRR |
|---|---|---|---|
| 0（默认） | 13.3% | 37.8% | 0.281 |
| 0.15 | 11.1% | 44.4% | 0.280 |
| 0.25 | 8.9% | 40.0% | 0.251 |

机制：词法路径已给标题 6:1 的权重（`rank.js` 的 `scoreEntry`），再往语义列塞一次标题是双计；而 RRF 融合时单路语义的改善被词法前排吃掉。结论：默认 0，旋钮保留但只有 >0 才物化标题行（改它会触发一次重建）。

**知识库语义。** 25 条共享条目、14 条改写查询（`eval/knowledge-eval.mjs`）：lexical 与 hybrid 同为 top-1 78.6% / top-3 92.9% / MRR 0.857，互换两条、净收益 0；无关问题的余弦峰值 0.471，高于 0.45 下限 → 接上就是泄漏。`VECTOR_SOURCES` 因此不含 `knowledge`，知识库继续走词法（它的标题本身就是强信号）。

### 7.4 热度、去重与多样性（2.0.0-beta.4）

三条从 AstrBot-LivingMemory 借来的排序手段。前两条先问「有没有东西可做」，再决定默认值：

**③ 去重 / MMR：没有可去的东西。** 新脚本 `eval/dupe-rate.mjs` 对每条查询的 top-3 两两算 Jaccard（`tokenize(title + preview)` 后的集合），真库 59 条查询（词法族 14 + 改写族 45，两种 mode 都跑）：**最大相似度 0.19**（词法族/lexical 0.15、改写族/hybrid 0.19），p90 ≤ 0.13。也就是说 0.5、0.75 两个阈值下重复率都是 **0%**——语料里根本没有近似重复。于是 `dedupe`、`mmr` 默认 0，实现保留（`dedupe` 贪心降权不删行、`mmr` 真 MMR 贪心），文档记「开了只是多算一次」。

**② 热度：默认开、只破平局。** `H = 1 + heat·(½·min(1, refs/10) + ½·min(1, (opens + exposed/4)/20))`，默认 `heat = 0.25`。

- `refs` = 引用入度：一次正则扫全语料（`CITE_ID = /(?:agent|j)-[a-z0-9]{4,16}/g`）统计有多少条正文提到它，替代逐条 O(n²) 扫描。
- `opens` 来自 `memory.open`（面板展开全文）；`exposed` 是「出现在结果页但没被打开」，权重 ¼，防「搜过就算重要」的自激。
- 计数落 `index/access.json`（`{version:1, entries:{"<src>:<id>":{opens, exposed, lastRead, lastExposed}}}`），2 s 合并写、原子 rename、上限 5000 键、保留 365 天，文件损坏时重建而不是报错。

**读取还会移动衰减参照时间**：`referenceTime = min(max(at, lastRead), at + 180d)`。400 天前的笔记被读一次，`decay` 从 `2^(-400/30) ≈ 0.0001` 回到 ≈1，分数涨 5 倍以上；180 天上限防一次误点永久免疫衰减。

为什么只破平局、不做 astrbot 那种 `0.5×相关 + 0.25×重要 + 0.25×新鲜`：真库里大多数查询只有一两条命中，强加的热度会开始**改变**排序而不是**打破**平局，而我们没有能测出这种改动的评测集（灵敏度 ±0.128 MRR）。所以热度是乘法因子、上限 0.5，且只在同分时起作用。

测试（`test-recall.mjs`）：引用者与被引者同分时被引者反超；两次打开再把同分翻转回来；`heat: 0` 恢复文件序；20 次重复查询 top-1 不变（曝光计数不得让结果自激漂移）；400 天前的笔记读一次分数 >5×。
